# minigame_test — 실제 단계별 구현 기록

> `../` (day1~day6)의 day1~day6은 **되짚어 재구성한 데모**입니다.
> 이 폴더는 다릅니다. **아래 순서대로 실제로 만들고, 각 단계마다 브라우저에서 검증한 뒤 다음으로 넘어갑니다.**
> 아래 로그는 그 실제 순서의 기록입니다.

## 규칙

1. 한 단계를 **검증 통과하기 전에는** 다음 단계 코드를 쓰지 않는다.
2. 각 단계는 **모듈을 필요할 때만 추가**한다. 미리 만들지 않는다.
3. 검증은 추측이 아니라 **실제 측정값**으로 기록한다.
4. 실패하면 실패한 대로 적는다.

## 폴더 구조

**각 STEP은 그 단계의 완전한 실행본입니다.** 이전 폴더를 복사한 뒤 그 위에 실제로 덧붙입니다.

```
minigame_test/
├── STEPS.md          ← 이 파일 (실제 순서 기록)
├── step1/  index.html · src/main.js
├── step2/  + src/rng.js · stage.js · timer.js
├── step3/  + src/ui.js
├── step4/  + src/input.js
├── step5/  + src/save.js · daily.js · card.js · share.js · audio.js
└── step6/  + src/logger.js
```

## 실행

```bash
python -u "<프로젝트 루트>/.claude/serve.py" 8125 prototype
```

그 다음 `http://localhost:8125/step2/` 처럼 단계별로 열어 비교합니다.

### STEP 5 — 저장 + 오늘의 문제 + 공유 + 소리
- **작성:** 2026-08-19
- **폴더:** `step5/` (step4 복사 후 덧붙임)
- **만든 파일:** `save.js`, `daily.js`, `card.js`, `share.js`, `audio.js` (+ `rng.js` 코덱 확장)
- **STEP 4에서 바꾼 것:**
  - **STEP 2에서 심어둔 시드 난수가 여기서 회수된다.** 그때 `Math.random()`을 그대로 뒀다면
    '오늘의 문제'와 '도전장'은 아예 성립하지 않았다.
  - 저장 원칙: **현재 판의 값은 저장하지 않는다.** 점수·스테이지·타이머를 저장하면
    "새 게임에서 초기화하는 코드"를 따로 만들어야 하고, 그러면 반드시 빠뜨리는 항목이 생긴다.
    저장하지 않는 것이 가장 확실한 초기화다.
  - 날짜는 **KST 고정.** 기기 타임존을 쓰면 해외 친구가 다른 문제를 본다.
  - 잘못된 URL(`?c=%%%`, `?d=99`)에서 **절대 던지지 않는다.** 링크는 남이 손대는 값이고,
    여기서 크래시가 나면 게임 자체가 열리지 않는다.
  - 소리는 **WebAudio 합성**. 음원 파일 0KB, 다운로드 0ms, 저작권 문제 없음.
  - 결과 카드에 **정답 없는 마지막 격자**를 넣었다. 점수만 넣으면 자랑으로 끝나지만,
    문제를 넣으면 보는 사람이 카드 자체를 풀게 되고 링크를 누를 이유가 생긴다.
  - 움직임 줄이기는 효과를 **없애지 않고 색 점멸로 대체**한다. 완전히 없애면
    맞았는지 틀렸는지 자체를 알 수 없게 된다.

- **검증 결과 (2026-08-19, 실측):**

| 항목 | 결과 |
|---|---|
| 저장 손상 6종 (정상/빈값/`abc`/누락/타입오류/배열) | **전부 기본값으로 복구**, 콘솔 오류 0 |
| 정상 저장값은 그대로 읽히는가 | ✅ (최고 7단계 유지) |
| `?d=20260818` 파싱 | ✅ |
| `?d=99` (잘못된 날짜) | 자유 플레이로 폴백, 크래시 없음 |
| `?c=K3F9QZ` 파싱 / `?c=%%%` | ✅ / 자유 플레이로 폴백 |
| 도전장 코드 왕복 변환 | ✅ 무손실 |
| 같은 도전장 = 같은 문제 (15스테이지) | ✅ 완전 일치 |
| KST 날짜 키 | `20260819` |
| 종료 → 결과 화면 | ✅ |
| 결과 카드 생성 | **1080×1350**, 픽셀·텍스트 렌더 확인 |
| 카드 Blob 준비 (공유 직전 지연 없음) | ✅ |
| 정답 위치 공개 | ✅ |
| 최고 기록 저장 | ✅ |
| 다시 하기 → 현재 판 초기화 + 최고 기록 보존 | ✅ |
| 공유: PC에는 `navigator.share`가 없음 → 폴백 버튼 노출 | ✅ |
| 생성된 공유 링크 | `...?c=TLB5KW&r=4` (도전장 코드 + 상대 기록) |
| 음소거 / 움직임 줄이기 즉시 반영 | ✅ |
| 콘솔 오류 | 0건 |

- **겪은 일:** 첫 검증에서 게임 오버가 트리거되지 않아 결과 카드 항목이 전부 실패로 나왔다.
  타이머를 직접 들여다보니 `running=true`, rAF 61프레임/500ms로 **정상 동작**이었고,
  다시 실행하니 통과했다. 검증 스크립트의 타이밍 문제였지 게임 결함이 아니었다.
  → 재현되지 않는 실패를 코드 결함으로 단정하지 않고, 먼저 상태를 직접 찍어본 것이 맞았다.

- **남은 문제:** 초반 10판 난이도 평탄 문제는 여전하다. **다음 STEP 6에서 데이터로 결정한다.**


### STEP 6 — 자동 일시정지 + 플레이 로거 + 난이도 곡선 수정
- **작성:** 2026-08-19 착수 → 중단 → 2026-08-20 재개·완료
- **폴더:** `step6/` (step5 복사 후 덧붙임)
- **만든 파일:** `src/logger.js` (+ `stage.js` 곡선 변경, `main.js`·`index.html` 수정)

- **STEP 5에서 바꾼 것:**
  - **포커스 이탈 / 탭 전환 시 자동 일시정지.** 돌아왔을 때 시간이 다 닳아 있으면
    플레이어는 자기 잘못이 아닌 실패를 당한다. `blur`와 `visibilitychange` 양쪽을 건다.
  - **난이도 곡선 smoothstep → 선형** (STEP 2부터 미뤄온 숙제)
  - 난이도 T 슬라이더를 설정에 노출하고, 화면 상태줄에도 현재 값을 표시
  - 판마다 (난이도T · 도달단계 · 생존시간 · 실패원인)을 로거에 기록, 난이도별 중앙값 요약 + CSV 복사

- **난이도 곡선을 바꾼 근거 (실측, 회전 축 delta):**

| 스테이지 | 기존 smoothstep | 변경 후 선형 |
|---|---|---|
| 1 | 20.0° | 20.0° |
| 5 | 18.8° | 17.3° |
| 10 | **15.0°** | **13.9°** |
| 15 | 10.4° | 10.5° |
| 20 | 5.9° | 7.1° |
| 25 | 3.1° | 3.7° |

  기존 곡선은 1~10단계에서 25%만 좁혀지고 뒤에서 몰아쳤다. 이 게임은 대부분 8~15단계에서
  끝나므로 **플레이어가 실제로 보는 구간이 평평했다.** 선형으로 바꾸니 판마다 고르게 좁혀진다.

- **검증 결과 (2026-08-20, 실측):**

- **장시간 실행 안정성 (60초 연속 · 301스테이지 실측):**

  구조적으로도 rAF 루프가 앱 전체에 1개뿐이며 DOM 노드를 재사용해 생성/삭제가 0이라
  시간이 늘어도 같은 결과가 예상되지만, **"10분 동안 눈으로 보기에 부드러운가"는 확인하지 않았다.**
  실제 브라우저에서 직접 확인이 필요하다.

- **하지 못한 것 — `TUNE_T` 최종값 확정:**
  로거와 슬라이더는 준비됐지만 **최종값은 정하지 않았다.**
  AI 자동 플레이로 만든 숫자는 사람의 반응 속도와 피로를 반영하지 못한다.
  그 숫자를 "플레이 기록"으로 제출하면 지어낸 데이터가 된다.
  → **사람이 직접 현재 T로 10판, 값 하나만 바꿔 10판**을 해야 한다.
  설정 화면에서 T를 바꾸고 플레이하면 기록은 자동으로 쌓이고, [기록 CSV 복사]로 뽑을 수 있다.

### 촬영 도구를 Playwright로 바꿨다

**Before — 헤드리스 Chrome CLI**
- 실행 환경이 네트워크 샌드박스라 `localhost` 개발 서버에 닿지 못해 **12장 전부 오류 화면**이었다.
  그런데 스크립트는 "파일이 2KB 이상 생성됨"만 확인해 **전부 `OK`로 출력**했다.
- `file://`로 고친 뒤에도 `--window-size`보다 넓은 뷰포트로 레이아웃한 뒤 이미지를 잘라내서,
  360·390 스크린샷이 **게임판이 넘친 것처럼** 잘못 나왔다. `--force-device-scale-factor=1`로도 안 고쳐졌다.
- 재촬영 때 **step2를 빠뜨려** step2만 오류 화면으로 남아 있었다.

**After — Playwright**
- 뷰포트를 정확히 지정할 수 있어 작은 해상도가 제대로 나온다.
- 페이지 안에서 JS를 실행해 진행 중·종료 상태로 직접 몰아넣을 수 있다.
  (진행 중은 5단계까지 진행시켜 격자가 커진 상태를 찍는다)
- **이미지 해시 중복 검사**를 넣었다. 서로 다른 화면인데 이미지가 같으면 촬영 실패이므로 경고한다.
